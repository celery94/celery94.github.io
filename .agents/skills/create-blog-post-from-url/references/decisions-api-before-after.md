# Decisions API 文章前后对比

这份对比以 `src/data/blog/1111-decisions-api-bounded-answers.md` 为“修改前”样本。它用来校准去 AI 味改稿，不用来替换已发布文章，也不能作为新文章的事实来源。

原文章的事实和接口说明可以保留。需要调整的是开场、标题、过渡、段落节奏和结尾。

## 1. 开头

### 修改前

> 一个客服 agent 每收到一句话，就要判断它属于账单、技术还是物流问题，还要决定是否紧急、是否需要人工接手。这些判断单独看都很简单，放进每天大量重复的流程后，等待时间和 token 成本会一起放大。
>
> OpenAI 在 2026 年 10 月 22 日正式开放 Decisions API。它仍然调用 `gpt-6-luna`，接口却只要求返回概率、固定选项或评分，官方给出的判断速度最高比 Responses API 快 10 倍。
>
> 这篇文章会说明它适合解决什么问题，并用一个工单分诊脚本串起三种答案类型。读完后，你能判断现有流程是否值得迁移，也知道第一次接入时该先定哪些边界。

### 修改后

> 客服工单里常有一句很短的话：「三天内扣了两次款，今天要处理。」
>
> 应用要同时决定交给哪个部门、是否插队、问题有多严重。每次判断都不复杂，但调用量一上来，延迟和费用就会显出来。
>
> OpenAI 在 10 月 22 日开放的 Decisions API 把这类调用收窄成三种结果：概率、固定选项和评分。模型只负责给出判断，业务代码继续执行路由、重试或人工审核。

### 改动原因

- 旧开头先讲抽象场景，再用“这篇文章会说明”转入文章。
- 新开头先放一句工单原话，读者立即知道系统在处理什么。
- 第三段去掉了阅读承诺，直接说明接口边界。

## 2. 小标题

### 修改前

```text
先看结论
请求由三部分组成
三种答案怎么选
写一个工单分诊脚本
设计问题比选择类型更重要
输入、缓存与限制
成本与实时语音
什么时候继续用 Responses API
下一步
```

### 修改后

```text
三类返回，对应三种业务动作
一次请求只有三个必填部分
工单该交给谁，先写成一个 choice
把分诊逻辑跑起来
阈值要从误判成本倒推
缓存只适合稳定的大段输入
什么时候该回到 Responses API
先挑一个错了还能人工接住的判断
```

### 改动原因

- `先看结论`和`下一步`可以放进很多文章，不能提示本篇内容。
- 新标题保留接口名称和任务对象，读者扫标题就能看到文章路径。
- 标题没有统一写成“为什么……”“如何……”，避免机械排比。
- 不要求每个标题都带数字或冒号，也不要求长度完全一致。

## 3. 结尾

### 修改前

> 从业务里找出一个每天频繁发生、答案范围固定、错了也有人能复核的判断。先用 Playground 准备一批覆盖典型情况和边界情况的真实样本，定义问题、选项和阈值，再把结果接到现有队列或规则引擎。
>
> 上线前重点观察三件事：答案类型是否稳定、低置信度比例是否可接受、人工复核是否能覆盖高风险结果。速度和费用只有在判断值得信任之后才有意义。
>
> 如果你正在把模型接进业务流程，Aide Hub 会继续分享 AI 助手、开发工具和软件工程实践，重点写清楚接口边界与失败处理。

### 修改后

> 先挑一个高频、答案有限、误判后还能人工接住的判断。准备一批覆盖正常工单和边界工单的样本，分别看漏判和误判的代价，再决定置信度阈值。
>
> 接口的速度和价格可以很快测出来。更值得先确认的是低置信度结果有没有出口，以及模型拒绝时业务能不能继续运行。这两件事没有答案，节省下来的等待时间也没有意义。

### 改动原因

- 旧结尾最后一段是固定关注语，和 Decisions API 的具体判断没有关系。
- 新结尾保留行动、风险边界和验证条件。
- 最后一段给出了判断标准，没有重新概括全文。

## 4. 过渡和总结句

### 修改前

```text
它解决的是「让模型做一个小判断」的问题，应用本身仍然负责业务规则和后续动作。

请求成功时，`answers` 中会出现三个同名结果。

脚本没有把模型结果直接当成最终业务状态。
```

### 修改后

```text
模型返回判断，应用决定是否路由、重试或转人工。

成功后返回的 `answers` 按 `name` 对应问题，读取时不需要依赖数组顺序。

置信度不足、答案类型不符或模型拒绝时，脚本统一转到 `human_review`。
```

### 改动原因

- 第一句删除了对文章价值的自我解释。
- 第二句补充了“按名称取值”的实际操作，不再只说请求成功。
- 第三句把回退条件写全，替代笼统的“没有直接当成最终状态”。

## 5. 结构密度

原文保留了三列表格和工单脚本。这些内容承担真实对比与操作，不属于 AI 味。

如果改成另一种写法，也不必为了“更自然”删掉全部结构。更合适的改法是：

- 保留答案类型对比表，因为它确实用于选型。
- 保留完整脚本，因为读者需要运行。
- 把“先看结论”的重复说明并回正文。
- 删除每个小节末尾的总结句。
- 不在每段结束后再补一条三 bullet 清单。

去 AI 味的目标是让具体信息推动文章，不要求把所有内容改成长段落。

## 6. 改稿后的整体变化

- 开头从抽象介绍变成一句真实工单。
- 标题从通用目录变成本篇对象和判断。
- 说明句减少，操作和后果增加。
- 段落长度不再完全一致。
- 固定关注语被具体风险边界替代。
- 技术事实、代码和参考链接保持不变。
