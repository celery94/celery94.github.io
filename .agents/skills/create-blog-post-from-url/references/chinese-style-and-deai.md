# 中文风格样本与去 AI 味改稿

这份参考用于起草前的语气校准，以及初稿完成后的第三轮编辑。它约束表达方式，不提供新事实，也不要求复刻下文样本的句子。

## 使用顺序

1. 起草前快速阅读「仓库写作样本」，确认本篇应采用的具体程度、句子节奏和判断方式。
2. 初稿完成后先做内容编辑，再做文字编辑。
3. 最后单独执行一次去 AI 味改稿。不要把它混在错别字或格式检查里。
4. 用户提供本人写作样本时，用户样本优先于仓库样本；仓库样本只用于参考，不能冒充用户声音，也不能把样本中的旧事实带进新文章。

## 仓库写作样本

这些段落来自现有文章，只提炼表达特点。不要复用其中的人物、时间、数字、产品结论或原句。

### 样本一：从具体失误进入

来源：`src/data/blog/1100-claude-code-context-for-dotnet-repository.md`

> 审查一个 agent 交上来的改动时，你发现它在 `csproj` 里加了一行带 `Version` 的 `PackageReference`。你的仓库用中央包管理，版本只写在 `Directory.Packages.props` 里，这一行现在和它打架。

可借鉴的地方：

- 第一段已经发生了一件事，读者能看到文件和错误。
- 作者没有先解释“仓库上下文为什么重要”，先让问题自己出现。
- 具体对象用代码标识，判断用普通中文。

### 样本二：先给现象，再解释契约

来源：`src/data/blog/1103-csharp-collections-access-mutation-ownership.md`

> 一个 `GetPendingAsync()` 方法返回 `IReadOnlyList<Request>`。调用方觉得拿到了只读数据，把它存进字段当作快照。之后别处继续往底层 `List<Request>` 里 `Add`，那个「快照」的 `Count` 也跟着涨了。

可借鉴的地方：

- 现象足够具体，读者能立即复现脑中的调用链。
- 句子短，但包含类型、动作和意外结果。
- 先让错误显得合理，再拆开其中的误解。

### 样本三：把选择写成一个可感知的场景

来源：`src/data/blog/1105-junior-developer-help-without-taking-over.md`

> 键盘就在你手边。一个初级开发者花了半天没定位的问题，你看两眼就大概知道问题在哪一行。这时有两种做法：把手伸过去，十分钟收工；或者坐下来，让他继续操作，你只负责问「你觉得是哪一步出的问题」。

可借鉴的地方：

- 开场有动作和取舍，读者能想象自己坐在那个位置。
- 没有用“沟通效率”“能力提升”这类抽象词代替场景。
- 两个选择都保留了合理性，后面的判断才有重量。

### 样本四：让“知道了”与“理解了”形成具体差距

来源：`src/data/blog/1110-sharing-information-without-overloading-engineers.md`

> 一个依赖的交付日期改了。你把四十条消息的讨论串转进团队频道，补一句「FYI」。有人以为这只是一般背景，继续按旧日期安排工作；也有人停下来读完，仍然不确定哪些结论已经定了。

可借鉴的地方：

- 用“四十条消息”“继续按旧日期”这类细节说明结果。
- 没有直接给读者贴“沟通失败”的标签，让事实先说话。
- 后续判断能落在注意力成本上，而不是泛泛讲透明度。

### 共同特点

- 开头先出现对象、动作、失败或选择。
- 抽象结论通常紧跟一个例子或后果。
- 段落长短不整齐，短段落用来推进动作，长段落用来解释关系。
- 作者会给出明确判断，同时保留判断的适用范围。
- 句子有书面表达，也有口语节奏，不刻意追求“金句”。

### 不要照搬的部分

- 不复制样本的开头句式。
- 不借用样本里的故事情节或数据。
- 不为了显得自然而强行加入“你”“我们”或职场经历。
- 不把技术文章改写成随笔。教程、接口说明和风险边界仍要写清楚。

## 禁用模板

以下规则分为两类：

- 硬性禁用：没有例外，起草和改稿时都不能使用。
- 默认禁用：只有在原文本身是 FAQ、清单，或用户明确要求保留某种格式时，才能说明理由后局部使用。

### 开头

| 禁用表达                                         | 常见问题                         |
| ------------------------------------------------ | -------------------------------- |
| 这篇文章会说明……读完后，你能……                  | 先介绍文章，再进入内容           |
| 本文将带你了解……                                 | 读者还没看到具体对象             |
| 在当今 AI 快速发展的时代……                       | 背景很大，信息很少               |
| 随着……的不断发展……                               | 时间背景替代了具体问题           |
| 让我们一起来看看……                               | 口播式过渡，技术文章里显得空     |
| 不可否认，……                                     | 先抬高语气，没有增加证据         |
| 如果你对……感兴趣，那么这篇文章适合你             | 用受众标签替代文章内容           |

以上开头模板全部硬性禁用。

改写方向：直接写正在发生的事、要完成的动作、已经出现的失败，或一个来自原文的明确结果。

### 小标题

默认禁用这些通用标题：

- `先看结论`
- `核心观点`
- `为什么重要`
- `深入解析`
- `关键洞察`
- `最佳实践`
- `总结`
- `写在最后`
- `下一步`
- `未来展望`

替换时优先写本篇独有的对象或判断，例如把「为什么重要」改成「缓存前缀至少要 1,024 个 token」，把「下一步」改成「先从一个高风险判断开始」。

### 过渡与总结

默认删除：

- `值得注意的是`
- `需要指出的是`
- `换句话说`
- `更重要的是`
- `从某种意义上说`
- `总的来说`
- `综上所述`
- `这意味着一件事`
- `这不仅说明了……也说明了……`

如果前后两段本来就连贯，直接删掉过渡句。需要补充因果时，写清楚是谁做了什么、导致了什么。

### 句子

硬性禁用：

- `不是……而是……` 及同类的强对称句式
- `真正的……是……`
- `本质上……`
- `核心在于……`
- `这不仅……更是……`

默认禁用：

- `从……到……，再到……` 的排比式空泛概括
- 连续三句都用相同长度和相同结构
- 每个小节结尾都补一句“这说明……”
- 每个概念都用加粗替代解释

检查默认禁用项时，重点看它们是否形成重复模式。

### 结尾

硬性禁用：

- `希望本文对你有帮助`
- `未来可期`
- `让我们拭目以待`
- `欢迎关注、点赞、转发`
- 固定的 Aide Hub 关注语

默认禁用：

- 用“总之”重新复述全文

微信发布需要关注引导时，写一句与本篇判断直接相关的话，或者省略。不要每篇使用同一句。

## 结构密度规则

### 表格

只在下面情况使用：

- 对比多个参数或方案。
- 列出接口字段、价格、版本或兼容矩阵。
- 原文本身是结构化清单。

如果三列表格只包含普通解释，改回段落。表格连续出现时，检查是否可以合并。

### 列表

- 列表用于步骤、条件、风险和参数。
- 连续两个列表之间至少放一段解释，除非它们本来就是同一组步骤。
- 不把每个段落都拆成三条 bullet。
- 不为了让文章“易读”而强行凑三项。

### 加粗

- 加粗只标真正需要扫读的结论、命令或风险。
- 一段里出现两处以上加粗时，检查是否有句子在争夺注意力。
- 不用加粗代替论证。

### 段落与章节

- 不要求每节长度相同。
- 不要求每节都以总结收尾。
- 允许一个章节只有两段，也允许关键章节更长。
- 章节顺序按读者理解推进，不按固定模板填满。

## AI 味从哪里来

文章出现下面现象时，优先检查表达，不必马上增加更多事实：

1. 开头可以原样套到另一篇文章。
2. 标题和小标题只说明“要讲什么”，没有本篇对象。
3. 每节第一句都在宣布下文，没有提供新信息。
4. 段落长度和句子结构过于整齐。
5. 结论句很多，具体例子很少。
6. 抽象名词承担了本应由动作和后果承担的工作。
7. 每一步都用“首先、其次、最后”连起来，即使这些步骤没有顺序。
8. 结尾重新概括全文，再补一句关注引导。
9. 文章能在不改变核心内容的情况下自动扩写到任意长度。
10. 删掉所有小标题后，段落之间没有自然关系。

这些是编辑信号，不作为机械扣分项。目标是让文章有具体内容和作者判断，避免用统一句法填满结构。

## 第三轮：去 AI 味改稿

这一轮不新增事实，不改变来源归属，只重写表达和组织。

### 1. 重写开头

读第一段，问自己：这段是否能原样放进另一篇文章？

如果答案是能，改成以下任一起点：

- 原文中的一个具体失败或意外结果。
- 读者马上要做的动作。
- 一个有条件的判断。
- 一组会改变选择的数字。

保留来源和作者信息时，把它们放到具体场景之后。

### 2. 检查标题链

只读标题和小标题：

- 是否知道文章讨论的对象。
- 是否能看出问题如何推进到结论。
- 是否存在“为什么重要”“深入解析”这类可替换标题。

把小标题改成短句或短判断，但不要写成夸张标题。标题可以朴素，只要本篇特有。

### 3. 检查每节第一句

每节第一句必须至少完成一项：

- 给出事实或数字。
- 描述一个动作。
- 提出本节要解决的冲突。
- 给出有依据的判断。

只负责“下面来看”“接下来讨论”的句子删除。

### 4. 删除重复过渡和总结

从第二节开始逐段检查：

- 上一段已经把关系说清时，删除本段开头的过渡。
- 一节结束时已经形成结论时，删除额外总结。
- 连续两个段落回答同一问题时合并。

尤其检查“这就说明”“这意味着”“由此可见”是否只是重复前一句。

### 5. 把抽象判断换成后果

遇到“提升效率”“降低成本”“增强可观测性”这类表述，往下追一层：

- 少了一次调用，还是少了一次人工分诊？
- 延迟从哪一段消失？
- 出错时谁会看到什么？
- 哪个现有流程需要改动？

原文没有提供量化结果时，写清条件和机制，不补数字。

### 6. 打破机械对称

检查全文是否出现：

- 每节三个 bullet。
- 每段四到五句。
- 每节长度接近。
- 每个小标题都是相同句式。
- 每节都以一句加粗结论结束。

只调整没有信息收益的统一结构。步骤、参数和条件仍然可以保留整齐格式。

### 7. 重写结尾

结尾应落在本篇的具体选择上：

- 读者下一步做什么。
- 什么条件下值得尝试。
- 哪些风险需要先验证。
- 还有什么问题没有答案。

删除全文复述和固定关注语。微信引导如果保留，必须和本篇主题直接相关。

### 8. 朗读检查

朗读开头、任意两个章节的接缝和结尾。遇到下面情况就改：

- 一句话需要回看才能断句。
- 连续出现相同节奏的短句。
- 过渡句可以被直接删除。
- 结尾像宣传稿或培训材料。

朗读检查用于发现机械节奏，不用来追求口语化。技术判断仍应保持准确。

## 发布前检查

去 AI 味改稿完成后逐项回答：

1. 开头是否包含本篇才有的对象、事件、数字或判断？
2. 是否命中了「禁用模板」中的固定开头、标题、过渡或结尾？
3. 小标题是否都能替换成另一篇文章而不显突兀？如果有，改成更具体的表达。
4. 每个主节第一句是否提供新信息，而不是宣布下文？
5. 是否存在可以整段删除、且不影响理解的总结或过渡？
6. 表格和列表是否承担了真实对比、步骤或条件？
7. 是否连续使用相同长度的段落、相同句式的标题或三项列表？
8. 抽象收益是否已经落到动作、后果或验证方式？
9. 结尾是否给出具体选择或风险边界，并删除了固定关注语？
10. 文章是否仍然准确、完整，没有为了“像人写的”改变事实或弱化技术说明？

任意一项不通过时先改稿。不要用增加新段落、更多加粗或更多表格掩盖结构问题。
