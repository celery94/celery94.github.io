## 取证顺序

优先使用具有页面渲染和交互能力的浏览器：

1. 打开原文，等待正文标题或内容容器出现。
2. 关闭 Cookie、登录、订阅等遮挡层。
3. 展开 `Read more`、折叠代码、分页和相关 Tab。
4. 提取标题、作者、日期、目录、正文、代码块、图片说明和引用链接。
5. 只跟进影响理解或操作的链接，优先官方文档、示例仓库、Part 2 和数据来源。
6. 把信息整理为按章节分组的笔记，记录每个补充链接提供了什么。

浏览器不可用且页面无需 JavaScript 渲染时，可用普通 HTTP 获取 HTML，依次读取：

- `<title>`、description、Open Graph、author、published time
- `<article>`、`<main>`，再回退到清理后的 `<body>`
- JSON-LD 或页面内嵌的结构化数据

原文依赖 JavaScript、登录或交互，而且无法取得完整正文时停止。不得根据标题、摘要和搜索片段补写成文。

超长原文先提取目录和分类框架。详细展开最关键的步骤或论点，其余内容合并概括；篇幅由保留证据和读者理解所需内容决定，不机械逐条翻译。

## 事实核对

- 至少记录 2–4 个原文锚点，例如分类、例子、数据、实验现象、代码或判断。
- 版本、价格、接口、产品能力、发布时间和兼容性需要核对最新官方资料。
- 原文与当前官方资料冲突时，正文采用当前事实，并注明原文当时的情况。
- 教程中的命令、参数、按钮、路径和错误信息优先用官方文档核对。
- 页面截图只能辅助判断；操作步骤以正文、代码和官方说明为准。
- 不补充无法追溯的数字、结论、案例或引用。

## 编辑提纲

写正文前先形成一份不进入文章的简短提纲，至少回答：

1. 目标读者此刻遇到什么问题，已经知道什么
2. 文章用一句话回答什么
3. 原文最值得保留的冲突、意外、案例或结果是什么
4. 中文文章增加什么价值
5. 读者看完能够做出什么决定或采取什么动作
6. 哪些背景、例子或旁支不影响结论，应当删除或合并

新增价值至少选择一种：核对后的当前事实、面向中文读者的解释或场景、
可运行示例、取舍分析、排错边界、行动清单，或围绕读者问题重新组织原文。
新增内容仍要有来源或明确的推理依据，不为追求差异补写事实。

提纲先确定核心结论和证据，再选择章节。不要默认保留原文的全部目录。

## 文章类型

先确定读者要带走的结果，再选择结构：

- 教程 / 实操：问题、前提、步骤、验证、常见问题
- 产品更新 / 发布：变化、目标用户、使用价值、限制
- 架构 / 系统设计：背景、组成、数据或控制流、取舍
- 观点 / 评论：观点、依据、反例、适用边界
- 研究 / 论文：问题、方法、发现、限制、现实意义
- 案例复盘：背景、决策、过程、结果、教训
- 工具评测：场景、体验、优缺点、门槛、替代方案

公众号分发判断只影响标题、摘要、结构和文末引导：

- 教程偏收藏
- 观点偏转发
- 工具评测偏关注
- 发布内容帮助读者判断是否值得尝试
- 研究内容重点建立可信度

不适合微信传播的内容仍可作为技术博客发布，避免包装成夸张文章。

## 开场与主线

开场直接进入读者关心的内容。根据材料选择一种自然方式：

- 一个具体问题、失败场景或使用困境
- 先展示结果，再解释原因和做法
- 一个有证据支持的反常识结论
- 原文中最有张力的事件、案例或对比

作者、来源和文章范围可以在开场之后交代。只有在说明适用边界确实有帮助时，
才使用「本文」「适合」「读完」等提示语，避免把三者组成固定开头。

文章主线应满足：

- 只看标题、小标题和每节第一句，也能读出问题、解释和结论的顺序。
- 每个主节回答一个明确问题，并增加事实、例子、判断或操作。
- 回答同一问题的章节合并；无法推动理解或行动的旁支删除。
- 教程尽早展示目标结果和最短可行路径，再补原理、变化和边界。
- 长篇技术内容按理解顺序逐步展开，背景资料放在读者需要它的位置。

## 写作规则

- 全文使用自然中文，专有名词保留英文，首次出现时可补中文解释。
- 生成独立重述，保留事实、必要代码、步骤和证据锚点。
- 避免逐段翻译、大段引用和原文结构的机械复制。
- 引用原文时只保留必要短句，并附来源。
- 先解释动机，再给代码、配置或步骤。
- 抽象说明之后尽快补充例子、代码、数据或具体场景。
- 结尾优先给出下一步操作、选型条件、风险边界或值得继续验证的问题。
- 公众号关注引导可以省略；需要时应与本篇主题直接相关，不重复固定宣传语。
- 不使用夸张、焦虑、空洞宣传和模板化过渡句。
- 正文语气由文章类型决定，不受随机封面风格影响。

## 两轮编辑

初稿完成后依次执行：

### 内容编辑

- 单独阅读标题、小标题和每节第一句，修正断裂、倒序或重复的论证路线。
- 检查每个主节是否带来新信息；合并回答同一问题的章节。
- 把最能帮助理解的结果、案例和证据前移。
- 删除只负责宣布下文、重复总结或连接上下文的段落。
- 确认新增解释没有超出来源和可验证事实。

### 文字编辑

- 拆开同时承载多个判断、读起来需要回看的长段落。
- 在抽象概念之后补充必要的具体例子，并删除不能帮助理解的装饰性例子。
- 删除同义反复、空泛转折和连续定义堆叠。
- 保留必要术语，首次出现时用一句自然中文解释。
- 检查结尾是否真正完成文章承诺，避免再次概括全文后接固定关注语。

不设置统一字数、段落长度或小标题数量。篇幅由核心问题、必要证据和读者完成
目标所需内容决定。

## 发布前内容审查

格式校验之前逐项回答：

1. 开头是否较快进入具体问题、结果、判断或事件？
2. 核心结论能否用一句话准确说清？
3. 文章是否提供了原文摘要之外的明确价值？
4. 标题、小标题和每节第一句是否形成连贯主线？
5. 是否存在整段删除后仍不影响理解或阅读节奏的内容？
6. 结尾是否给出行动、选择条件、风险边界或后续问题？

任何一项不满足时先修改文章。若缺少来源材料导致核心结论、证据或新增价值
无法成立，停止封面、微信发布、提交和推送，并说明缺失内容。

## 教程要求

教程至少交代：

1. 要解决的问题、适用场景和不适用场景
2. 软件版本、账号、权限、环境变量等前置条件
3. 按顺序排列的完整步骤
4. 每一步的目的、输入、操作和预期结果
5. 成功验证方式
6. 常见错误及优先检查项

一个熟悉该领域但没有做过这件事的读者，应能直接照着文章完成操作。

## 标题与摘要

- 主标题准确说明技术对象与具体收益或适用场景。
- 默认发布微信时，标题最多 32 个字符。
- 避免标题党、悬念句、生僻词和抽象大词。
- 小标题保持简短，像目录，不写成长句。
- `description` 控制在 80–120 个字符，直接说明问题、受众和收获。
- `title` 与 `description` 不使用中文弯引号 `“”‘’`，需要强调时使用「」。
- 不承诺没有提供的资料、源码、课程、社群、福利或账号能力。

## 图片与引用

- 保留步骤截图、结果图、流程图、架构图和数据图。
- 过滤头像、导航图标、广告图和无信息量装饰图。
- 图片保存到 `src/assets/{ID}/`，放在对应正文附近并补充中文 `alt`。
- 正文路径使用 `../../assets/{ID}/{filename}`。
- 文末保留 `## 参考`，至少包含原文链接。
- 只列出正文真正使用的来源，通常不超过 10 条。

## Frontmatter

文件路径为 `src/data/blog/{ID}-{slug}.md`，`slug` 使用唯一的
kebab-case。

```yaml
---
pubDatetime: YYYY-MM-DDTHH:mm:ss+08:00
title: "最多 32 个字符的中文标题"
description: "80-120 个字符的中文摘要"
tags: ["Tag1", "Tag2"]
slug: "unique-kebab-case"
ogImage: "../../assets/{ID}/01-cover.{ext}"
source: "https://example.com/original"
---
```

- `pubDatetime` 默认使用 Asia/Shanghai 当前时间减 20 分钟，必须带
  `+08:00`。
- 只有用户明确要求定时发布时才允许未来时间。
- 用户明确不要封面时省略 `ogImage`。
- `source` 始终写原文 URL，补充来源放入文末参考。
